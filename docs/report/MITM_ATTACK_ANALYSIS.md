## Executive Summary

This report demonstrates the critical importance of **digital signatures** in preventing Man-in-the-Middle (MITM) attacks during cryptographic key exchange protocols.

### Key Findings:

| Metric | Without Signatures | With Signatures |
|--------|-------------------|-----------------|
| **MITM Vulnerability** | ❌ Vulnerable | ✅ Secure |
| **Attack Success Rate** | 100% | 0% |

## Attack Methodology

### MITM Attack Overview

A Man-in-the-Middle attack occurs when an adversary positions themselves between two communicating parties and intercepts/modifies their messages.

**Attack Model:**
```
┌─────────┐         ┌──────────┐         ┌─────────┐
│  Alice  │ ◄─────► │ Attacker │ ◄─────► │   Bob   │
└─────────┘         └──────────┘         └─────────┘
                    (Intercepts &
                     Modifies Traffic)
```

**Attacker Capabilities:**
- ✓ Intercept all network traffic
- ✓ Modify messages in transit
- ✓ Inject fake messages
- ✓ Generate own cryptographic keys
- ✗ Cannot obtain Alice's or Bob's private keys

**Attack Goal:**
Establish separate shared secrets with Alice and Bob, allowing decryption of all messages.

## Vulnerable Implementation

### Protocol: Diffie-Hellman WITHOUT Signatures

#### Attack Flow:

```
Step 1: Alice generates DH keypair
   Alice: generates (a_private, A_public)
   Alice → Network: A_public

Step 2: Attacker intercepts
   Attacker: generates (x_private, X_public)
   Attacker → Bob: X_public (pretending to be Alice)

Step 3: Bob generates DH keypair
   Bob: generates (b_private, B_public)
   Bob → Network: B_public

Step 4: Attacker intercepts
   Attacker → Alice: Y_public (pretending to be Bob)
   (Y is another key generated by attacker)

Step 5: Shared Secret Computation
   Alice computes: K1 = DH(a_private, Y_public)
   Bob computes:   K2 = DH(b_private, X_public)
   Attacker computes: K1 = DH(y_private, A_public)
                      K2 = DH(x_private, B_public)

Result: Alice and Bob have DIFFERENT secrets!
        Attacker knows BOTH secrets!
```

#### Analysis:

**Observation 1:** Alice's secret ≠ Bob's secret  
**Observation 2:** Attacker-Alice secret = Alice's secret  
**Observation 3:** Attacker-Bob secret = Bob's secret  

**Impact:**
- Alice encrypts message M with K1: C1 = AES-Encrypt(K1, M)
- Attacker decrypts: M = AES-Decrypt(K1, C1) ✓ SUCCESS
- Attacker reads/modifies M → M'
- Attacker re-encrypts: C2 = AES-Encrypt(K2, M')
- Bob decrypts: M' = AES-Decrypt(K2, C2)
- **Bob receives attacker's message, not Alice's!**

**Verdict:** ❌ **MITM ATTACK SUCCESSFUL**

## Secure Implementation

### Protocol: ECDH WITH Digital Signatures (ECDSA)

#### Secure Flow:

```
Pre-Requisite: Long-term Key Distribution
   Alice generates: (SignKey_A_private, SignKey_A_public)
   Bob generates:   (SignKey_B_private, SignKey_B_public)
   Exchange SignKey_A_public ↔ SignKey_B_public via authenticated channel
   (Both parties store each other's trusted public keys)

Step 1: Alice generates ephemeral ECDH keypair
   Alice: generates (a_private, A_public)
   
Step 2: Alice SIGNS ephemeral public key
   Payload = { A_public, timestamp, sender: Alice, receiver: Bob }
   Signature = ECDSA-Sign(SignKey_A_private, Payload)
   Alice → Network: { Payload, Signature, SignKey_A_public }

Step 3: Attacker attempts MITM
   Attacker: generates (x_private, X_public)
   Attacker creates: Payload' = { X_public, timestamp, sender: Alice, ... }
   Problem: Attacker doesn't have SignKey_A_private!
   
   Option A: Send unsigned → Bob rejects (no signature)
   Option B: Sign with attacker's key → Bob rejects (wrong signature)

Step 4: Bob receives and VERIFIES
   Bob: verifies Signature using SignKey_A_public (trusted)
   Verification: ECDSA-Verify(SignKey_A_public, Signature, Payload)
   
   If attacker modified Payload:
      Signature ≠ Valid(SignKey_A_public, Modified_Payload)
      → REJECT message
      → Alert: Possible MITM attack!

Result: Only authentic keys are accepted
        MITM attack is PREVENTED
```

#### Demonstration Results:

```

========================================

   Alice Signing Public Key (trusted)

   Ephemeral Public: 041bd6ab4336099854e7c0c3ba6f2207...

   Attacker Ephemeral Public: 04dd43a52d07b32142987b1f4652694...

4️⃣  Bob receives the message and VERIFIES signature
   ✅ Alice's signature: VALID
   Ephemeral key is authenticated and trusted

   🛡️  Attacker's fake signature: REJECTED

```

#### Analysis:

**Observation 1:** Alice's signature verified successfully ✓  
**Observation 2:** Attacker cannot forge Alice's signature ✗  
**Observation 3:** Bob rejects any unsigned or incorrectly signed keys ✓  

**Security Properties:**
- **Authentication:** Signature proves key came from Alice
- **Integrity:** Any modification detected immediately
- **Non-repudiation:** Only Alice can create valid signature
- **MITM Prevention:** Attacker cannot replace keys undetected

**Verdict:** ✅ **MITM ATTACK PREVENTED**

## Code Analysis

### Implementation in Our System

#### Client-Side: Signature Generation

**File:** `client/src/crypto/KeyExchange/initiateExchange.js`

```javascript
// Generate ephemeral ECDH keypair
const eph = await subtle.generateKey(
  { name: 'ECDH', namedCurve: 'P-256' },
  true,
  ['deriveKey', 'deriveBits']
);

// Export public key
const rawPub = await subtle.exportKey('raw', eph.publicKey);
const ephPubB64 = btoa(String.fromCharCode(...new Uint8Array(rawPub)));

// Create payload
const payload = JSON.stringify({
  ephPub: ephPubB64,
  timestamp: Math.floor(Date.now() / 1000),
  sender: keys.username,
  receiver: targetUser.username
});

// SIGN payload with long-term ECDSA private key
const payloadBytes = new TextEncoder().encode(payload);
const sigBuf = await subtle.sign(
  { name: 'ECDSA', hash: 'SHA-256' },
  keys.signing.privateKey,  // Long-term key
  payloadBytes
);

const signatureB64 = btoa(String.fromCharCode(...new Uint8Array(sigBuf)));

// Send: { payload, signature, publicKey }
```

**Security Features:**
- ✅ Ephemeral key signed with long-term private key
- ✅ Payload includes timestamp (prevents replay)
- ✅ Payload specifies sender and receiver (prevents redirect)
- ✅ ECDSA P-256 with SHA-256 (cryptographically strong)

#### Client-Side: Signature Verification

**File:** `client/src/crypto/KeyExchange/respondExchange.js`

```javascript
// Import sender's public key
const pubKeyBytes = Uint8Array.from(atob(packet.pubKeyB64), c => c.charCodeAt(0));
const senderPublicKey = await subtle.importKey(
  'spki',
  pubKeyBytes,
  { name: 'ECDSA', namedCurve: 'P-256' },
  true,
  ['verify']
);

// VERIFY signature before accepting ANY key
const payloadBytes = new TextEncoder().encode(packet.payload);
const signatureBytes = Uint8Array.from(atob(packet.signature), c => c.charCodeAt(0));

const isValid = await subtle.verify(
  { name: 'ECDSA', hash: 'SHA-256' },
  senderPublicKey,
  signatureBytes,
  payloadBytes
);

if (!isValid) {
  throw new Error('Invalid signature - possible MITM attack detected!');
}

// Only if valid, proceed with key exchange
const ephPubBytes = Uint8Array.from(atob(payloadData.ephPub), c => c.charCodeAt(0));
// ... import and use ephemeral public key
```

**Security Features:**
- ✅ Verification happens BEFORE accepting any key
- ✅ Invalid signature throws error immediately
- ✅ No keys used if signature fails
- ✅ Clear error message for security event logging

#### Server-Side: Double Verification

**File:** `server/src/controllers/keyExchangeController.js`

```javascript
export const initiateKeyExchange = async (req, res) => {
  const { targetUserId, publicData } = req.body;
  
  // Server-side verification (defense in depth)
  const isValid = await verifySignature(
    publicData.payload,
    publicData.signature,
    publicData.pubKeyB64
  );

  if (!isValid) {
    // Log potential attack
    await auditLog({
      userId: req.user.id,
      action: 'INVALID_KEY_EXCHANGE_SIGNATURE',
      result: 'BLOCKED',
      metadata: { targetUserId }
    });
    
    return res.status(400).json({ 
      error: 'Invalid signature - possible MITM attack' 
    });
  }

  // Proceed only if signature is valid
  // ...
};
```

**Security Features:**
- ✅ Server validates signatures (defense in depth)
- ✅ Audit logging for security events
- ✅ Attack attempts logged for analysis

## Defense Mechanisms

### 1. Long-term Key Distribution

**Method:** Out-of-band authenticated exchange
- Users exchange ECDSA public keys during registration
- Server acts as trusted intermediary
- Keys transmitted over TLS (HTTPS)
- Keys stored in IndexedDB (client-side)

**Why It Works:**
- Initial exchange is authenticated by server
- Keys are trusted because source is verified
- Attacker cannot inject fake keys during registration

### 2. Mandatory Signature Verification

**Policy:** Zero-tolerance for unsigned keys
- Every ephemeral public key MUST be signed
- Every signature MUST be verified
- No exceptions, no fallbacks
- Verification failure = immediate rejection

**Why It Works:**
- Attacker cannot bypass signature check
- Modified keys are instantly detected
- No way to "downgrade" to unsigned protocol

### 3. Timestamp Validation

**Method:** 5-minute freshness window
```javascript
const payloadData = JSON.parse(packet.payload);
const now = Math.floor(Date.now() / 1000);
const age = Math.abs(now - payloadData.timestamp);

if (age > 300) {  // 5 minutes
  throw new Error('Signature too old - possible replay attack');
}
```

**Why It Works:**
- Prevents replay of old (valid) signatures
- Limits window for attack attempts
- Forces attacker to act in real-time

### 4. Ephemeral Keys (Forward Secrecy)

**Method:** New keys for each session
- Ephemeral keys generated fresh each time
- Never reused across sessions
- Destroyed after session ends

**Why It Works:**
- Compromise of long-term key doesn't decrypt past sessions
- Attacker must actively MITM each session (will be caught)
- Perfect forward secrecy guaranteed

## Attack Surface Analysis

### What Attacker CAN Do:

✓ Intercept all network traffic  
✓ See all public keys and signatures  
✓ Generate own cryptographic keys  
✓ Attempt to modify messages  
✓ Attempt to inject fake keys  

### What Attacker CANNOT Do:

✗ Obtain Alice's or Bob's private signing keys  
✗ Forge signatures without private keys  
✗ Modify signed payloads without detection  
✗ Bypass signature verification  
✗ Decrypt messages encrypted with proper shared secret  

### Attack Complexity:

| Attack Type | Complexity | Success Probability |
|------------|-----------|---------------------|
| MITM on unsigned DH | Trivial | 100% |
| MITM on signed ECDH | Infeasible | ~0% (2^-256) |
| Forge ECDSA signature | Breaking P-256 | ~0% (2^-128) |
| Brute force private key | 2^256 operations | Computationally infeasible |

## Conclusion

### Findings

1. **Diffie-Hellman without signatures is completely vulnerable to MITM attacks**
   - Demonstrated 100% success rate for attacker
   - Alice and Bob establish different shared secrets
   - Attacker can decrypt all messages

2. **Digital signatures (ECDSA) prevent MITM attacks**
   - Demonstrated 0% success rate for attacker
   - Signature verification detects all tampering
   - Only authenticated keys are accepted

3. **Our implementation is secure**
   - Uses ECDSA P-256 for signatures
   - Mandatory signature verification
   - Defense-in-depth with client and server checks
   - Audit logging for attack attempts

### Recommendations

✅ **Always use digital signatures for key exchange**  
✅ **Verify signatures before accepting ANY public key**  
✅ **Use authenticated channel for initial key distribution**  
✅ **Implement timestamp validation to prevent replay**  
✅ **Use ephemeral keys for forward secrecy**  
✅ **Log all signature verification failures**
